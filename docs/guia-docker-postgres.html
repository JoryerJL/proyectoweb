Docker + PostgreSQL + Django

Guía paso a paso de todo lo que hicimos en el Laboratorio 08 del proyecto Canaco, explicada desde cero para que la entiendas y puedas repetirla tú solo.

1. Resumen: qué hicimos

El Laboratorio 08 pide conectar el proyecto a una base de datos real, crear las tablas y un usuario administrador. El PDF usa MySQL con XAMPP; nosotros usamos PostgreSQL dentro de Docker, que es lo que se usa mucho en la industria.

  1. Creamos docker-compose.yml: una "receta" que le dice a Docker que levante un servidor PostgreSQL.
  2. Descubrimos que los puertos 5432 y 5433 ya los usaba tu Postgres local, así que elegimos el 5434.
  3. Arrancamos Docker Desktop y levantamos el contenedor con docker compose up -d.
  4. Cambiamos canaco/settings.py para que Django use PostgreSQL en vez de SQLite.
  5. Escribimos los 6 modelos del lab en home/models.py.
  6. Generamos y aplicamos las migraciones (makemigrations y migrate), y con eso se crearon las tablas.
  7. Creamos el superusuario superadmin para entrar al panel /admin.
  8. Verificamos con psql que las tablas existen dentro del contenedor.

2. ¿Qué es Docker?

Imagina que quieres instalar PostgreSQL. Sin Docker tendrías que descargarlo, instalarlo en tu Mac, configurarlo, y si otro proyecto necesita otra versión… empiezan los conflictos (justo lo que ya tienes: Postgres 14 y 17 instalados con Homebrew peleando por puertos).

Docker te deja correr programas dentro de cajas aisladas llamadas contenedores. Cada caja trae todo lo que el programa necesita y no toca el resto de tu computadora.

Analogía Piensa en un contenedor de barco. No importa si dentro hay plátanos o computadoras: el barco lo transporta igual. Docker hace lo mismo con programas: PostgreSQL, Redis, MySQL… todos se manejan con los mismos comandos.

¿Por qué es mejor que XAMPP o instalarlo directo?

Sin DockerCon Docker
Instalas Postgres en tu Mac para siempre.Lo prendes y apagas cuando quieras; si lo borras, tu Mac queda limpia.
Una sola versión a la vez (o conflictos).Puedes tener Postgres 14, 16 y 17 en contenedores distintos sin problema.
Cada compañero lo configura distinto.Todos usan el mismo docker-compose.yml, así que todos tienen exactamente lo mismo.
Configurar usuario/contraseña a mano.Se declara en un archivo de texto y se crea solo.

Docker Desktop

En Mac, Docker funciona a través de la app Docker Desktop (la ballena 🐳 en la barra de arriba). Esa app corre el "motor" de Docker (el daemon). Si Docker Desktop está cerrado, ningún comando docker funciona.

Cuando empezamos, el comando docker ps dio este error:

failed to connect to the docker API at unix:///Users/.../docker.sock
... check if the daemon is running

Eso significa "el motor no está prendido". Lo arreglamos abriendo la app:

open -a Docker
ConsejoEspera a que la ballena deje de animarse (unos 30–60 segundos la primera vez). Puedes comprobar que ya está listo con docker info: si no marca error, ya está.

3. Los 5 conceptos clave

Con estos cinco conceptos entiendes el 90% de Docker para desarrollo:

1Imagen

Es la plantilla o "molde" de solo lectura. Por ejemplo, la imagen postgres:17 contiene PostgreSQL versión 17 ya instalado. Se descargan de Docker Hub, una especie de "tienda" pública de imágenes.

postgres es el nombre y 17 es la etiqueta (tag), que normalmente es la versión.

2Contenedor

Es una copia en ejecución de una imagen. Si la imagen es la receta del pastel, el contenedor es el pastel. De una imagen puedes crear muchos contenedores. El nuestro se llama canaco_db.

3Volumen

Los contenedores son desechables: si borras uno, todo lo que tenía adentro desaparece. Un volumen es una carpeta que Docker guarda fuera del contenedor para que los datos sobrevivan. Nuestro volumen se llama canaco_pgdata y ahí viven tus tablas y registros.

ImportanteSin volumen, cada vez que recrearas el contenedor perderías la base de datos completa (tablas, superusuario, noticias…).

4Puerto (port mapping)

El contenedor es una caja cerrada. Para que Django (que corre en tu Mac) pueda hablar con Postgres (que corre dentro de la caja) hay que abrir una ventana: conectar un puerto de tu Mac con un puerto del contenedor. Lo vemos a detalle en la siguiente sección.

5Docker Compose

En lugar de escribir un comando larguísimo para crear el contenedor, describimos todo en un archivo docker-compose.yml y lo levantamos con un solo comando: docker compose up -d.

docker-compose.yml ──(docker compose up)──▶ descarga IMAGEN postgres:17 │ ▼ crea CONTENEDOR canaco_db ├── datos en VOLUMEN canaco_pgdata └── PUERTO 5434 (Mac) ─▶ 5432 (contenedor)

4. Puertos (y por qué usamos 5434)

Un puerto es como el número de departamento dentro de un edificio. Tu computadora es el edificio (dirección localhost o 127.0.0.1) y cada programa que recibe conexiones vive en un "departamento" numerado:

  • Django (runserver) → puerto 8000
  • PostgreSQL → puerto 5432 por defecto
  • MySQL → puerto 3306 por defecto

Regla de oro: dos programas no pueden escuchar en el mismo puerto al mismo tiempo.

Lo que nos pasó

Al primer intento, Django se conectó al puerto 5432 y respondió:

FATAL:  role "canaco" does not exist

¡Raro! Ni siquiera habíamos levantado el contenedor. Eso significaba que ya había otro Postgres en ese puerto. Lo investigamos así:

# ¿Quién está escuchando en el puerto 5432?
lsof -nP -iTCP:5432 -sTCP:LISTEN

# ¿Qué servicios de Homebrew están corriendo?
brew services list

Resultado: tenías postgresql@14 y postgresql@17 de Homebrew ocupando el 5432 y el 5433. En lugar de apagarlos (podrías usarlos en otros proyectos), buscamos un puerto libre:

for p in 5432 5433 5434 5435; do
  printf "$p: "
  lsof -nP -iTCP:$p -sTCP:LISTEN >/dev/null && echo ocupado || echo libre
done
5432: ocupado
5433: ocupado
5434: libre
5435: libre

Cómo funciona el mapeo "5434:5432"

TU MAC CONTENEDOR canaco_db ┌──────────────────┐ ┌──────────────────────┐ │ Django │ │ │ │ se conecta a │ ── localhost:5434 ─▶ 5432 PostgreSQL 17 │ │ localhost:5434 │ │ │ └──────────────────┘ └──────────────────────┘ (5432 y 5433 siguen siendo de tus Postgres de Homebrew)

El formato siempre es "PUERTO_EN_TU_MAC:PUERTO_DENTRO_DEL_CONTENEDOR". Dentro del contenedor Postgres sigue usando su 5432 normal; solo cambiamos la "puerta de entrada" en tu Mac.

Para recordarIzquierda = afuera (tu Mac). Derecha = adentro (el contenedor).

5. El archivo docker-compose.yml

Está en la raíz del proyecto. Es un archivo YAML: un formato de texto donde la indentación (espacios) importa, igual que en Python. Nunca uses tabuladores, solo espacios.

services:                          # lista de contenedores que queremos
  db:                              # nombre del servicio (lo inventamos nosotros)
    image: postgres:17              # imagen a usar: PostgreSQL versión 17
    container_name: canaco_db      # nombre fijo del contenedor
    restart: unless-stopped       # si reinicias la Mac, se vuelve a prender solo
    environment:                   # variables que configura la imagen de postgres
      POSTGRES_DB: canaco          # crea una base llamada canaco
      POSTGRES_USER: canaco        # crea el usuario canaco
      POSTGRES_PASSWORD: canaco    # con contraseña canaco
    ports:
      - "5434:5432"                # puerto Mac 5434 ─▶ puerto contenedor 5432
    volumes:
      - canaco_pgdata:/var/lib/postgresql/data  # donde Postgres guarda los datos

volumes:
  canaco_pgdata:                   # declaramos el volumen con nombre

Línea por línea

ClaveQué hace
servicesCada servicio se convierte en un contenedor. Aquí solo tenemos uno (db), pero más adelante podrías agregar otro, por ejemplo redis.
imageQué imagen descargar de Docker Hub. La primera vez tarda porque descarga unos ~150 MB; después ya queda guardada.
container_nameSin esto Docker inventaría un nombre como proyectoweb-db-1. Con nombre fijo es más fácil escribir comandos.
restartunless-stopped: arranca solo cuando abres Docker Desktop, a menos que tú lo hayas detenido a propósito.
environmentLa imagen oficial de Postgres lee estas variables solo la primera vez (cuando el volumen está vacío) para crear la base y el usuario.
portsEl mapeo de puertos explicado arriba.
volumes (dentro de db)Conecta el volumen canaco_pgdata con la carpeta donde Postgres guarda sus archivos dentro del contenedor.
volumes (al final)Declara que ese volumen existe y lo administra Docker.
Ojo con las variables de environmentSi después cambias POSTGRES_PASSWORD en el archivo, no se actualiza, porque el volumen ya tiene una base creada. Para que tome efecto tendrías que borrar el volumen (y con él los datos). Lo vemos en Problemas comunes.
SeguridadUsuario y contraseña canaco/canaco están bien para desarrollo en tu computadora. En un servidor real nunca uses contraseñas así ni las subas a GitHub.

6. Levantar el contenedor

Desde la carpeta del proyecto (donde está el docker-compose.yml):

cd ~/Documents/m4/repos/proyectoweb
docker compose up -d
  • docker compose es la herramienta que lee el archivo docker-compose.yml.
  • up significa "crea y arranca todo lo que dice el archivo".
  • -d (detached) lo deja corriendo en segundo plano y te devuelve la terminal. Sin -d verías los logs en vivo y al cerrar la terminal se apagaría.

La salida fue:

 Volume proyectoweb_canaco_pgdata Created     ← creó el volumen
 Container canaco_db Creating                ← creó el contenedor
 Container canaco_db Created
 Container canaco_db Starting
 Container canaco_db Started                 ← ¡corriendo!
¿Por qué el volumen dice proyectoweb_canaco_pgdata?Compose le antepone el nombre de la carpeta del proyecto (proyectoweb) para no mezclar volúmenes de proyectos distintos.

¿Ya está listo para recibir conexiones?

Postgres tarda unos segundos en arrancar. Lo comprobamos con pg_isready, un programa que viene dentro del contenedor:

docker exec canaco_db pg_isready -U canaco -d canaco

docker exec = "ejecuta este comando dentro del contenedor canaco_db". Si responde accepting connections, ya está.

Ver que está corriendo

docker ps
NAMES       PORTS                      STATUS
canaco_db   0.0.0.0:5434->5432/tcp     Up 22 seconds

Aquí confirmas el nombre, el mapeo de puertos y que está Up (encendido). También lo puedes ver en la app Docker Desktop, en la pestaña Containers.

7. Conectar Django: canaco/settings.py

Django necesita saber qué base de datos usar y cómo llegar a ella. Antes usaba SQLite (un archivo, db.sqlite3). Lo cambiamos así:

import os
from pathlib import Path
# ...

DATABASES = {
    'default': {
        'ENGINE': 'django.db.backends.postgresql',
        'NAME': os.environ.get('DB_NAME', 'canaco'),
        'USER': os.environ.get('DB_USER', 'canaco'),
        'PASSWORD': os.environ.get('DB_PASSWORD', 'canaco'),
        'HOST': os.environ.get('DB_HOST', 'localhost'),
        'PORT': os.environ.get('DB_PORT', '5434'),
    }
}
ClaveValorDebe coincidir con…
ENGINEpostgresqlEl tipo de base de datos (antes era sqlite3; el lab usaba mysql).
NAMEcanacoPOSTGRES_DB del compose
USERcanacoPOSTGRES_USER
PASSWORDcanacoPOSTGRES_PASSWORD
HOSTlocalhostTu propia Mac (el contenedor publica el puerto ahí).
PORT5434El número de la izquierda en "5434:5432"

¿Qué es os.environ.get('DB_PORT', '5434')?

Lee una variable de entorno llamada DB_PORT. Si no existe, usa '5434' como valor por defecto. Así, si un compañero tiene la base en otro puerto, no edita el código, solo hace:

DB_PORT=5435 python manage.py runserver

El "traductor": psycopg

Python no sabe hablar con PostgreSQL por sí solo. Necesita un driver (conector). Para Postgres es psycopg, que ya estaba en tu pyproject.toml. Comprobamos que estuviera instalado:

uv sync
.venv/bin/python -c "import psycopg; print(psycopg.__version__)"
# 3.3.6
Comparación con el labCon MySQL habrías necesitado el paquete mysqlclient. Con Postgres es psycopg. Todo lo demás de Django (modelos, migraciones, ORM) funciona exactamente igual: esa es la ventaja de Django.

8. Los modelos: home/models.py

Un modelo es una clase de Python que representa una tabla. Cada atributo es una columna. Django lee tus modelos y escribe el SQL por ti.

class Categoria(models.Model):          # ─▶ una tabla
    nombre = models.CharField(max_length=60)              # ─▶ columna VARCHAR(60)
    createdat = models.DateTimeField(auto_now_add=True)   # ─▶ fecha de creación automática
    updatedat = models.DateTimeField(null=True, blank=True)
    fk_user = models.ForeignKey(User, on_delete=models.SET_NULL, null=True, blank=True)

    class Meta:
        managed = True               # Django crea/modifica esta tabla
        db_table = 'categoria'        # nombre real de la tabla en Postgres
        verbose_name_plural = 'Categoria'   # cómo se ve en /admin

    def __str__(self):
        return self.nombre        # cómo se muestra un registro (en el admin, en print...)

Los 6 modelos y cómo se relacionan

¿Por qué home_perfil y no perfil?El PDF no le pone class Meta con db_table al modelo Perfil. Cuando no lo indicas, Django nombra la tabla nombreapp_nombremodelo, o sea home_perfil.

on_delete: ¿qué pasa si borro al "padre"?

  • CASCADE: borra también a los hijos. Si borras una publicación, se borran sus comentarios.
  • SET_NULL: deja el campo vacío. Si borras una categoría, sus noticias quedan "sin categoría" (por eso necesita null=True).

choices: valores permitidos

ESTADOS = [
    ('borrador', 'Borrador'),     # (lo que se guarda en la BD, lo que ve el usuario)
    ('publicado', 'Publicado'),
]
estado = models.CharField(max_length=20, choices=ESTADOS, default='borrador')

9. Migraciones

Escribir el modelo no crea la tabla. Hay dos pasos:

models.py ──makemigrations──▶ home/migrations/0001_initial.py ──migrate──▶ tablas en Postgres (tu código) (instrucciones: "plan de obra") (la obra hecha)

Paso 1: makemigrations — escribir el plan

.venv/bin/python manage.py makemigrations home
Migrations for 'home':
  home/migrations/0001_initial.py
    + Create model Archivo
    + Create model Categoria
    + Create model Perfil
    + Create model Publicacion
    + Create model GaleriaPublicacion
    + Create model Comentario

Django comparó tus modelos con las migraciones anteriores (no había ninguna) y generó el archivo 0001_initial.py. Este archivo sí se sube a Git, porque es el historial de cambios de tu base de datos.

Paso 2: migrate — ejecutar el plan

.venv/bin/python manage.py migrate
  Applying contenttypes.0001_initial... OK
  Applying auth.0001_initial... OK
  ...
  Applying home.0001_initial... OK
  Applying sessions.0001_initial... OK

Aplicó las migraciones de Django (usuarios, sesiones, admin…) y la nuestra (home.0001_initial). Django guarda cuáles ya aplicó en la tabla django_migrations, así que si lo corres otra vez no repite nada.

Regla para el futuroCada vez que cambies models.py (agregar un campo, una tabla, etc.): makemigrations y luego migrate. Siempre en ese orden.

11. Verificar dentro de Postgres (el "phpMyAdmin" de la terminal)

El lab usa phpMyAdmin para ver las tablas. Con Postgres podemos usar psql, la consola oficial, que ya viene dentro del contenedor.

Comando rápido (una sola consulta)

docker exec canaco_db psql -U canaco -d canaco -c "\dt"
  • docker exec canaco_db: ejecuta algo dentro del contenedor.
  • psql -U canaco -d canaco: entra a Postgres con el usuario canaco a la base canaco.
  • -c "\dt": ejecuta el comando \dt, que lista las tablas (describe tables).
 public | archivo                    | table | canaco
 public | categoria                  | table | canaco
 public | comentario                 | table | canaco
 public | galeria_publicacion        | table | canaco
 public | home_perfil                | table | canaco
 public | publicacion                | table | canaco
 ...y las de Django: auth_user, django_session, etc.

Modo interactivo

docker exec -it canaco_db psql -U canaco -d canaco

-it = interactivo con terminal. Ahora puedes escribir SQL directamente:

canaco=# \dt                              -- listar tablas
canaco=# \d publicacion                   -- ver columnas de una tabla
canaco=# SELECT username, email FROM auth_user;
canaco=# \q                               -- salir
¿Prefieres algo visual como phpMyAdmin?Puedes usar TablePlus, DBeaver o pgAdmin (o la pestaña Database de PyCharm). Conéctate con: host localhost, puerto 5434, usuario canaco, contraseña canaco, base canaco.

12. Tu rutina diaria

  1. Abre Docker Desktop (o open -a Docker) y espera a que esté listo.
  2. Levanta la base (si ya está corriendo no pasa nada, solo dice "Running"): 
    cd ~/Documents/m4/repos/proyectoweb
docker compose up -d
  3. Arranca Django: 
    .venv/bin/python manage.py runserver
  4. Al terminar (opcional, para liberar memoria): 
    docker compose stop
¿Y si reinicio la Mac?Gracias a restart: unless-stopped, el contenedor se prende solo cuando abres Docker Desktop (salvo que lo hayas detenido con stop). Tus datos siguen ahí porque viven en el volumen.

14. Problemas comunes y cómo resolverlos

"failed to connect to the docker API… is the daemon running?"

Docker Desktop está cerrado. Ábrelo con open -a Docker y espera a que docker info funcione.

"port is already allocated" o "address already in use" al hacer up

Otro programa ya usa ese puerto. Revisa quién con lsof -nP -iTCP:5434 -sTCP:LISTEN. Cambia el número de la izquierda en ports (por ejemplo "5435:5432") y también PORT en settings.py. Luego docker compose up -d de nuevo.

Django dice: "role 'canaco' does not exist"

Te estás conectando a otro Postgres (por ejemplo el de Homebrew en 5432), no al del contenedor. Revisa que PORT en settings.py sea 5434 y que no tengas una variable DB_PORT distinta en tu terminal (echo $DB_PORT).

Django dice: "connection refused" en el puerto 5434

El contenedor no está corriendo. Revisa con docker ps. Si no aparece, docker compose up -d. Si aparece pero acaba de arrancar, espera unos segundos (pg_isready).

Cambié la contraseña en docker-compose.yml y ahora no conecta

Las variables POSTGRES_* solo se usan al crear el volumen la primera vez. Tienes dos opciones:

  • Regresar la contraseña anterior en el archivo, o
  • Empezar de cero (borra todos los datos): docker compose down -v, luego docker compose up -d, migrate y createsuperuser otra vez.
Quiero reiniciar la base desde cero 
docker compose down -v          # borra contenedor y datos
docker compose up -d            # base nueva y vacía
.venv/bin/python manage.py migrate
.venv/bin/python manage.py createsuperuser
¿Qué pasa con el archivo db.sqlite3?

Ya no se usa. Era la base anterior. Puedes dejarlo o borrarlo; Django ahora solo habla con Postgres.

15. Ejercicios para practicar

Hazlos en orden. Ninguno borra datos, salvo que se indique.

  1. Ejecuta docker ps e identifica el nombre, el puerto y el estado de tu contenedor.
  2. Apágalo con docker compose stop, intenta abrir /admin y observa el error. Luego préndelo con docker compose start y vuelve a probar.
  3. Entra a la consola SQL con docker exec -it canaco_db psql -U canaco -d canaco y ejecuta \d categoria. Compara las columnas con el modelo Categoria.
  4. Inserta una categoría a mano: 
    INSERT INTO categoria (nombre, createdat) VALUES ('Economía', now());
SELECT * FROM categoria;
  5. Ve los logs de Postgres con docker compose logs -f db mientras recargas una página de Django.
  6. Ejecuta python manage.py showmigrations home y fíjate en la [X] de 0001_initial.
  7. Reto: haz docker compose down (sin -v) y luego up -d. Comprueba que tu categoría y el superadmin siguen ahí. Eso demuestra que el volumen funciona.
